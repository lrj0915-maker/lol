# 质量关卡 — 交付标准（Definition of Done）

本文件定义了所有代码变更的最低交付标准。这不是建议，是强制要求。
任何不满足以下标准的工作，不得视为"完成"。

## 核心原则

1. 绝不偷工减料。宁可多花时间做对，也不要交付半成品。
2. 交付前必须自我验证。不要假设代码是对的，要证明它是对的。
3. 每次变更都要比之前更好，至少不能更差。

## 交付检查清单（每次变更必须逐项确认）

### 代码完整性
- [ ] 所有修改的功能都已完整实现，没有 TODO、FIXME、HACK 占位符遗留
- [ ] 没有注释掉的代码块残留
- [ ] 没有遗留 `.bak`、`.old`、`.tmp` 文件
- [ ] 新增的后端 API 方法已同步到 bridge.py 和 bridge.js（参考 bridge-sync.md）
- [ ] 前端修改后已确认需要 `npm run build`

### 代码质量
- [ ] 无语法错误（使用 getDiagnostics 工具验证）
- [ ] 无裸 except（`except:` 必须改为 `except Exception:`）
- [ ] 无调试用 print 语句（使用 logger 模块）
- [ ] 无重复代码（相同逻辑必须抽取为共享函数）
- [ ] 无硬编码路径（使用 `os.path.join`）
- [ ] 无未使用的 import
- [ ] 代码注释使用中文

### 功能验证
- [ ] 修改的代码不会破坏现有功能（检查调用链）
- [ ] 边界情况已考虑（空值、None、空列表、网络超时）
- [ ] 错误处理完整（不会因异常导致程序崩溃）
- [ ] 线程安全（共享状态有锁保护）

### 一致性
- [ ] 命名风格一致（Python: snake_case，JS: camelCase）
- [ ] 返回值格式一致（后端方法返回 dict 含 success 字段，或 list）
- [ ] 错误信封格式一致（前端 bridge.js 的 _makeErrorEnvelope）
- [ ] UI 风格一致（遵循 variables.css 定义的主题色和间距）

## 禁止的偷工减料行为

以下行为视为未完成交付，必须修正后才能提交：

1. 只改了一半就说"完成了" — 如果任务涉及前后端，两端都要改完
2. 用 `pass` 或空函数占位 — 要么实现，要么明确说明为什么不实现
3. 复制粘贴代码而不抽取公共函数 — DRY 原则不可妥协
4. 跳过错误处理 — "先跑起来再说"不是借口
5. 不验证就交付 — 必须用 getDiagnostics 检查，必须确认调用链完整
6. 留下调试代码 — print、console.log、debugger 语句必须清理

## 验证流程

完成编码后，按以下顺序验证：

1. 对所有修改的文件运行 getDiagnostics，确认零错误
2. 检查 bridge.py 和 bridge.js 的方法是否一一对应
3. 检查是否有遗留的调试代码（print/console.log）
4. 检查是否有新引入的裸 except
5. 确认所有新增文件都在正确的目录下
6. 如果修改了前端，提醒用户执行 `npm run build`

只有以上全部通过，才能告知用户"完成"。
